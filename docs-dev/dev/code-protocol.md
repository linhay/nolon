# Nolon 代码协议

## 1. 目标与范围
- 目标：统一 Nolon 仓库内代码实现、评审、测试和发布前校验的最低标准，降低回归与维护成本。
- 范围：适用于 `nolon/`、`libs/Providers/`、测试工程与文档配套变更。

## 2. 强制边界
- 架构边界：`nolon` app 层只做编排，不承载 Codex CLI/app-server 的进程与 JSON-RPC 细节。
- Provider 边界：Codex 运行时、进程、协议与快照逻辑必须落在 `libs/Providers`。
- UI 设计边界：颜色统一使用 `DesignSystem.Colors`，禁止直接使用系统默认色值常量。
- 本地化边界：新增 UI 文案必须写入 `Localizable.xcstrings`，禁止散落硬编码字符串。

## 3. 开发流程协议（必须）
1. 先写 BDD 场景与验收条件。
2. 先补失败测试（红灯）。
3. 最小实现使测试通过（绿灯）。
4. 必要重构并保持测试通过。
5. 更新 docs-dev 与 memory，保证信息一致。

## 4. 代码实现协议
- 并发：UI 状态更新使用 `@MainActor`；跨线程共享模型满足 `Sendable`。
- 日志：生产代码禁止 `print()`，使用结构化日志或明确错误传播。
- 文件监听/事件流：优先单一信号聚合（如 Combine debounce），避免多层抑制导致事件丢失。
- 命名：文件名、类型名、测试名保持语义可检索，避免缩写歧义。

## 5. 测试协议（必须）
- 功能改动必须配对应测试（新增或更新）。
- 优先覆盖行为边界、异常路径、竞态/时序风险。
- 未执行测试时，必须在变更说明里标注原因与风险。

## 6. 提交与发布协议
- 提交粒度：小步可回滚，避免混合无关改动。
- 提交信息：使用 Conventional Commits（如 `feat:`, `fix:`, `docs:`, `chore:`）。
- 发布前：工作区需干净，构建与核心测试通过，再执行发布脚本。

## 7. DoD（完成定义）
- 验收场景满足。
- 相关测试通过（或已明确阻塞与风险）。
- 文档已落到 `docs-dev` 正确目录。
- 关键决策已写入 `memory/YYYY-MM-DD.md`，并完成索引同步。
