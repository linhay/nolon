## 这段会话真正做成了什么

这不是一段单点修 bug 会话，而是一条完整的 `Codex Sessions` 产品化推进链。它依次推动了：

1. 页面定位重定
   - 从“迁移优先、诊断可达”转向“`project` 会话浏览优先，迁移与诊断可达”。
2. 大列表浏览模型重构
   - 默认先看项目，再看组内最近会话。
   - 大规模会话场景中，优先保证可滚动、可浏览、可预测。
3. 缓存与刷新策略成型
   - 从“每次打开就全量扫”转向“缓存先展示，后台 reconcile，按 stale 刷新”。
4. 详情交互收口
   - 从列表底部大详情卡转向会话行内展开。
5. 进一步的持久化与内存收敛
   - 明确 `projection cache`、`usage index`、流式 rollout 解析分别解决什么问题。

## 会话里反复出现的用户核心诉求

### 1. 稳定浏览比实时刷新更重要
- 用户明确表示：“其实刷新可以不用这么实时。”
- 这意味着 `Codex Sessions` 不能以“每次都追最新”作为默认优化目标。
- 正确方向是：
  - 先有内容可看
  - 列表顺序稳定
  - 后台慢慢补新数据
  - 只有 stale 才重新刷新

### 2. 大规模数据下不能跳
- 用户真实数据量在 `3000+` 会话量级。
- 在这个量级下，任何“边扫边全量重排”的方案都会让 section/row 持续跳动，直接破坏浏览体验。
- 所以排序、分组、缓存应用都必须优先保证视觉稳定。

### 3. 缓存必须对首屏有实际价值
- 用户多次追问“不是做过缓存吗”“为什么还是会持续在扫”。
- 这说明“缓存存在”不等于“用户受益”。
- 只有能直接恢复 `projects / sections / rows` 的缓存，才算首屏缓存。

### 4. 详情必须就地展开
- 用户明确要求点会话后直接在该条下方展开。
- 本质上这是大列表中的“视觉焦点保持”问题，不只是样式偏好。

### 5. 先文档和计划，再进入实现
- 用户在会话中多次强调：
  - 先落实文档和执行计划
  - 补完之后直接开始执行
- 这已经不是建议，而是该模块的工作方式要求。

## 稳定共识

## 1. 产品语义共识
- `Codex Sessions` 的主任务是“项目维度会话浏览”。
- 迁移、分享、诊断、文件定位都属于在浏览主线上的可达能力。
- 任何新的 UI 改动，都不能把页面再拉回“操作面板优先”的 IA。

## 2. 性能架构共识
- 进程内缓存只解决当前进程复用，不解决重启后的首屏问题。
- 因此需要磁盘级投影缓存来恢复最终 UI 投影。
- `usage index` 不能只缓存 usage totals，最终扩展到 timeline 元数据才真正减少详情重复扫描。
- 大文件 rollout 解析必须走流式读取，不能整文件读入内存。

## 3. 刷新策略共识
- 默认不是实时监听 + 实时刷新。
- 首屏优先读缓存。
- 后台 reconcile。
- App 激活或页面重入只在 stale 时刷新。

## 4. 交互结构共识
- 会话详情以内联展开为主。
- 组头与会话行尽量共享相似的信息轨道结构。
- 次级动作尽量收敛到菜单或上下文操作，不占据主浏览空间。

## 5. 工程边界共识
- rollout 扫描、缓存、usage、timeline、SQLite 容错在 `libs/Providers`。
- 分组、排序、搜索、展开态、选择态在 ViewModel。
- UI 结构化模型与共享组件放 `libs/NolonUIFoundation` / `libs/NolonUI`。
- 不能由 App 层直接解析 rollout 细节。
