## Micro-Sync 5
- 调查 Nolon -> Codex MCP 同步后的启动告警，结论是当前主因不是 Codex `config.toml` 语法错误，而是把环境依赖型 MCP 也全量启用了：
  - `figma-desktop` 当前指向 `http://127.0.0.1:3845/mcp`，现场 `curl` 直连失败，本机没有对应本地 HTTP server 在监听，增大 `startup_timeout_sec` 无法解决。
  - `xcode-tools` 当前写入的 `MCP_XCODE_PID=39964` / `MCP_XCODE_SESSION_ID=F669D5FD-D672-4C88-8AA8-ADC3E12B6355` 已失效，`ps -p 39964` 无进程；这类会话型 bridge 不适合长期常驻启用。
  - `chrome-devtools` / `mobile-mcp` / `api-mocker-mcp` / `context7` / `figma` / `stitch` 在 Codex 启动时都会被 eager initialize；若服务端握手慢、需 OAuth、需外部应用配合或首次拉起浏览器/设备桥接，会直接产生命令行 warning。
  - 本机 live `~/.codex/config.toml` 目前这些 server 全部是 `enabled` 且未写任何 `startup_timeout_sec`。
- 对照官方文档与参考 Codex 源码后确认：
  - Codex 官方 MCP TOML 以 `command` / `url` 推断 transport；`enabled`、`required`、`startup_timeout_sec`、`tool_timeout_sec` 是共享字段。
  - Nolon 当前写出的 Codex MCP 区块形态基本正确，不是因为 `type = "http"` / `type = "stdio"` 没写才报错。
  - Nolon 本地 `CodexMCPServer` 模型仍未覆盖官方支持的 `cwd` 与 `bearer_token_env_var`，后续若要做完整上游对齐，需要补齐这两个字段的读写与 UI round-trip。
- 后续行动建议：
  - P0：同步到 Codex 时，对 `figma-desktop`、`xcode-tools` 这类运行时强依赖外部会话的 MCP 引入“环境可用性”判断或默认 `enabled = false` 策略。
  - P1：给已知慢启动的 MCP 提供 `startup_timeout_sec` 模板/预设，而不是依赖用户手改 `config.toml`。
  - P2：补齐 `cwd`、`bearer_token_env_var` 的 Codex MCP 模型对齐与回归测试。
