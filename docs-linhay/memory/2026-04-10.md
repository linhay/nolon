## Codex API key / OAuth `config.toml` 联动修复
- 目标：修复 Codex API key relay 账号激活后只切换 `auth.json`、未同步 `config.toml` 的问题，并保证 relay / OAuth / 官方 API key 切换时 `config.toml` 状态一致。
- 关键决策：
  - 不在 gateway patch 逻辑上叠逻辑，单独新增 `CodexActiveProviderConfigManager` 管理 relay provider patch / restore。
  - 激活态联动直接挂到 `CodexAuthManager.activateAccountAndMarkActive(...)`、`preflightManagedAuthIfNeeded(...)`、`reconcileDetachedProviderAuthIfNeeded(...)`，覆盖真实切换与自愈路径。
  - 编辑当前激活 API key 账号后，额外调用 `refreshActiveProviderConfigIfNeeded(...)` 立即刷新 `config.toml`。
- 新增根因确认：
  - API key relay 账号表单里的 `Model Provider` 候选错误地来自 `models_cache.json`，导致保存进账号快照的是模型 slug，而不是 provider id。
  - 这会让后续 `config.toml` patch 使用错误的 provider id，形成“顶层 `model_provider` 与 section / 账号快照不一致”的混合状态。
  - 用户侧可能表现为 `Codex protocol error: transport: JSON-RPC process terminated`。
- `config.toml` 托管字段：
  - 顶层：
    - `model = "gpt-5.4"`
    - `model_reasoning_effort = "xhigh"`
    - `model_provider = "<sanitized-provider-id>"`
  - section：
    - `[model_providers.<sanitized-provider-id>]`
    - `name`
    - `base_url`
    - `query_params`
    - `http_headers`
    - `requires_openai_auth = true`
    - `wire_api = "responses"`
- 切换策略：
  - relay API key 激活：写入托管 provider 配置
  - OAuth / 官方 API key 激活：恢复 relay 接管前原始 `config.toml`
  - gateway 虚拟账号激活：跳过，不覆盖 gateway 配置
- 关联修复：
  - `CodexModelPreferenceService.loadRelayModelProviderIDs(for:)` 从 `config.toml` 提取 relay provider id，替换原来的 models cache 建议源。
  - `ProviderUsageEngine+CodexManagement` 对 relay 草稿新增 `modelProvider` 必填校验。
  - `makeConfiguredAccountPayload(...)` 现在会同步顶层 `base_url`，修复编辑当前激活 relay 账号后仍读取旧 `base_url` 的问题。
- 兼容结论：
  - 修复后，新建 relay 账号会保存正确 provider id。
  - 新增激活态兼容修复：如果历史 relay 坏快照缺少 `nolon.relay.model_provider`，但当前 `config.toml` 已有同 `base_url` 的唯一 provider section，则激活时会自动推断并回写快照。
  - 仍无法自动修复的旧账号是：
    - 已被错误保存成模型名而不是 provider id
    - 当前 `config.toml` 里同一 `base_url` 存在多个 provider section，无法唯一判定
  - 上述无法唯一判定的旧账号，仍需重新编辑保存一次或重建。
- 验证：
  - `xcodebuild build -project nolon.xcodeproj -scheme NolonResourceKit -destination 'platform=macOS'` 已通过。
  - `xcodebuild test -project nolon.xcodeproj -scheme nolon-tests -destination 'platform=macOS' -only-testing:nolonTests/ProviderUsageEngineValidateConfiguredAccountTests` 已通过，6 个测试 0 失败。
- `swift test --package-path libs/Providers --filter CodexConfiguredAccountTests` 仍被仓库现有第三方依赖问题阻塞，不是本次改动引入：
  - `libs/Providers/.build/checkouts/swift-collections/Sources/ContainersPreview/Extensions/TemporaryAllocation.swift`

## Codex API key 历史会话可见性修复
- 目标：修复切到 relay API key 账号后，Codex 恢复列表 / `resume --last` 看不到旧历史会话的问题。
- 根因确认：
  - 上游 Codex 恢复历史默认按当前 `model_provider` 过滤。
  - 过滤同时依赖 rollout 文件头部 `session_meta.payload.model_provider` 和 `state_4.sqlite` 的 `threads.model_provider`。
  - Nolon 激活 relay API key 时把顶层 `model_provider` 切到 relay provider，导致旧 `openai` 历史被过滤隐藏，而不是丢失。
- 决策：
  - 不改上游 Codex 行为，在 Nolon 激活 / 恢复当前 provider 时补一层历史 provider 兼容迁移。
  - 新增 `CodexSessionProviderMigrationManager`，同步迁移：
    - `sessions/**/*.jsonl`
    - `archived_sessions/**/*.jsonl`
    - `state_*.sqlite`
- 迁移策略：
  - OAuth / 官方 provider -> relay provider：把基础 provider 历史迁到当前 relay provider。
  - relay provider -> OAuth / 官方 provider：把当前 relay 历史迁回基础 provider。
  - relay provider id 变化：把旧 relay provider 历史迁到新 relay provider。
  - 基础 provider 优先取 relay 接管前原始 `config.toml` 中的顶层 `model_provider`，缺失时回退 `openai`。
- 测试与验证：
  - 新增 `CodexAuthManagerTests` 中的历史 provider 迁移场景，覆盖 rollout + archived rollout + state db 的双向迁移。
  - `xcodebuild build -project nolon.xcodeproj -scheme nolon-tests -destination 'platform=macOS'` 已通过。
  - `swift test --package-path libs/Providers --filter CodexAuthManagerTests` 被仓库现有第三方依赖问题阻塞，不是本次改动引入：
    - `libs/Providers/.build/checkouts/swift-collections/Sources/ContainersPreview/Extensions/TemporaryAllocation.swift`
    - `thrown expression type 'any Error' cannot be converted to error type 'E'`
