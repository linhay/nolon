# 2026-04-28

## CodexAuthManager SQLite 化测试收口
- 继续收拢 `CodexAuthManager` 在 SQLite / managed-active auth 模型下的测试口径，修正大量仍按旧快照文件布局断言的用例。
- 测试层统一改为优先读取 `accountAuthData(for:)` / `accountAuthDataWithoutMaterialization(for:)`，不再默认把 `accountAuthFile(account)` 当成真实数据源。
- 活动账号相关断言改为匹配当前实现：provider `auth.json` 激活后指向 `managedActiveAuthFolder(...)/auth.json`，活动账号注册表按 canonical provider key / 已配置 provider 清洗。
- 修复 `reconcileProviderAuthWithSnapshotsIfNeeded(for:)` 的一个真实问题：当 provider `auth.json` symlink 仍指向旧 snapshot，但活动账号注册表已经指向新账号时，预检现在会优先重链到注册表声明的 active snapshot，而不是保留陈旧链接。
- 用户进一步把规则收紧为：外部程序修改 provider `auth.json`` 后，只要新 payload 还能形成稳定唯一身份（当前按 `email + account_id` 或 `api_key(+base_url)` 识别），就继续托管并切换到对应账号；只有身份不足或歧义时，才放弃托管。
- 已新增持久化的 “paused provider auth management” 状态；`usage_load` / `background_poll` 发现外部漂移后，如果 identity 稳定就继续托管并更新 active selection，如果 identity 不稳定才清空 app 内 active selection、撤回托管 relay 配置，但保留外部 `auth.json` 原样存在并停止后续接管。
- 运行中监听 `pollProviderAuthChange` 也已改为统一走被动预检分流逻辑，不再把外部改动无条件直接回灌到我们自己的 active snapshot。
- 一旦用户在 app 内重新执行 `activateAccountAndMarkActive`，暂停状态会被清掉，托管和监听恢复。
- 整组 `swift test --package-path libs/Providers --filter CodexAuthManager` 已重新打绿，当前为 100 条通过。

## Codex auth takeover debate 结论
- 通过 `debate` 圆桌复核后确认：当前“稳定身份继续托管，不稳定身份退选暂停”的总方向是对的，但实现上还有两个明确缺口。
- 缺口一：`paused` 对 `background_poll` 的单向门问题已经修掉。现在暂停后不会停止监听；若外部随后把 `auth.json` 改成稳定身份，轮询会自动解除 paused 并恢复托管。
- 对 `api_key` 可能重复创建 snapshot 的风险做了定向回归验证，当前代码下未复现；已补测试锁定“同一稳定 API key 漂移不会新增 snapshot”。
