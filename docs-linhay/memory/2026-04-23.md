- 用户反馈：`Codex` 用量页里只有最近两天有 `requests` 数据，更早日期虽有 token 用量，但 `requests = 0`，不符合“有用量就会有请求；没有用量可以没有请求”的口径。
- 本地 SQLite 取证结论：
  - `~/Library/Application Support/Nolon/codex-sessions/usage-index-v1.sqlite` 中，`2026-04-21` 往前多天 `SUM(total_tokens) > 0` 但 `SUM(request_count) = 0`；
  - 最近两天才开始出现正常 `requests`；
  - 说明不是图表聚合层漏算，而是历史 minute cache 一直没被重扫回填。
- 这轮确认的根因：
  - `CodexSessionUsageIndex.load(...)` 之前只检查“文件没变 / archived hash 命中 / minute rows 存在”，没有识别“旧 minute rows 带 token 但 `request_count = 0`”这一类 legacy cache；
  - 因此历史 rollout 一旦命中旧缓存，就会持续走 `cacheHit`；
  - 即使文件后来继续增长，也可能继续走 `deltaAppend`，把旧的缺失 requests 历史分钟桶保留下来。
- 已落实的修复策略：
  - 在 `CodexSessionUsageIndex` 新增 `hasRequestlessTokenUsageMinuteEntries(...)`；
  - 只要某个 rollout 的 minute rows 存在 “`input/cached/output` 任一大于 0，但 `request_count <= 0`” 的记录，就判定该缓存需要回填；
  - 该条件同时阻止 `cacheHit` 和 `deltaAppend`，强制走 `fullRebuild`，从原始 rollout 重新写 minute requests。
- 新增回归测试：
  - `loadSessionUsageBackfillsMissingRequestCountsOnCacheHit`
  - `loadSessionUsagePrefersFullRebuildOverDeltaAppendWhenRequestCountsNeedBackfill`
- 验证结果：
  - `swift test --package-path libs/Providers --filter CodexSessionStoreTests` 通过；
  - `swift test --package-path libs/Providers --filter CodexTokenTrendServiceTests` 通过；
  - `git diff --check` 通过。

## Codex 首轮全量扫描进度缺失根因与修复
- 现象：清空 `Codex` 用量缓存后重新进入 `Usage`，页面只显示 spinner，没有“当前文件 / 当前阶段 / x/x 进度”。
- 根因：空缓存场景走 `CodexSessionStore.prepareProjectedUsageIndex(...)`，此前这条路径不会发 `performanceNotification`；而 `ProviderUsageEngine` 只监听 `refresh_projected_usage_day_keys`，导致 UI 完全收不到首轮建索引进度。
- 修复：在 `prepareProjectedUsageIndex(...)` 新增 `prepare_projected_usage_index` 进度事件，分阶段发送 `scan_inventory / read_usage_index / reconcile_rollouts / analyze_rollout / rollout_completed / purge_stale_entries / finished`，并附带 `current_rollout_path`、`processed_rollout_count`、`dirty_rollout_count`、`refreshed_live_rollout_count`、`refreshed_archived_rollout_count`、数据库路径等字段。
- UI 接线：`ProviderUsageEngine` 已同步接入 `prepare_projected_usage_index`，首轮全量扫描现在会显示阶段文案、当前 rollout 文件名、`x / x` 进度和进度条比例。

## Codex 超大 archived rollout 导致索引长时间卡在单文件
- 现象：全量扫描进度卡在 `467 / 2728`，一直显示正在解析 `archived_sessions/rollout-2026-04-16T18-36-37-019d95dd-3e24-7340-a13d-2dc50749fa46.jsonl`。
- 现场证据：
  - 文件大小约 `153 MB`
  - 共 `15186` 行
  - 第 `13887` 行单行约 `50 MB`
  - 该超大行属于 `response_item -> function_call_output`，不包含 `token_count`
- 根因：旧实现虽然不会把这类 `response_item` 计入 usage，但仍会：
  - 在 `parseUsageEventLine(...)` 里对整行做全文搜索；
  - 更严重的是在 `parseUsageFile(...)` 里为了 timeline 再次调用 `parseRolloutLine(data:)`，导致对这条 `50 MB` 单行做第二次整段 JSON decode。
- 修复：
  - 新增 `CodexSessionEventParser.fastTopLevelEnvelope(data:) / fastTopLevelTimestamp(data:)`，按字节扫描顶层 `timestamp/type`；
  - `parseUsageEventLine(...)` 先用顶层 `type` 决定是否直接跳过；
  - `parseUsageFile(...)` 的 timeline 更新不再对整行做 `parseRolloutLine(data:)`，改为复用 `fastTopLevelTimestamp(data:)`。

## Usage intraday 新增 1min bucket
- 用户追加需求：`Codex -> Usage` 的 intraday drilldown 需要支持真正的一分钟级数据展示，而不是继续停留在 `15 / 30 / 60min`。
- 这轮收敛结论：
  - `ProviderIntradayBucket` 新增 `minute1`，展示文案为 `1min`；
  - `ProviderUsageRegistry` 改为 provider-aware 暴露：
    - `Codex`: `1min / 15min / 30min / 60min`
    - `Gemini / Claude / Antigravity`: `1min / 5min / 10min / 15min / 30min / 60min`
  - `CodexIntradayUsageService` 不再基于 quarter-hour packed buckets 做 intraday 聚合，而是直接读取 `CodexSessionStore` 的 projected minute usage，再按 bucket seconds 派生，确保 `1min` 是真实分钟事实，不是伪精度。
