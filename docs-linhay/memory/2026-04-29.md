## CloudKit 启动崩溃修复

- 背景：线上 `nolon 2.1.20 (202604282246)` 在启动期主线程崩溃，栈顶位于 `CloudKit`，回溯到 `CodexiCloudSyncService.shared` 初始化。
- 根因结论：
  - `CodexiCloudSyncLiveCoordinator` 在启动时 eager 构造 `CKContainer(identifier:)`。
  - 发布脚本 `scripts/build-dmg.sh` 先 `CODE_SIGNING_ALLOWED=NO` 构建，再手工 `codesign`，但之前未显式带 `nolon/nolon.entitlements`。
  - 导致线上包实际缺少 CloudKit entitlement，`CKContainer` 在系统框架内部直接 `SIGTRAP`。
- 已完成修复：
  - `CodexiCloudSyncService` 改为按运行时 entitlement 惰性创建 `CodexiCloudSyncLiveCoordinator`，缺 entitlement 时直接降级为 `unavailable`，不再启动即崩。
  - `scripts/build-dmg.sh` 的 app 重签名显式追加 `--entitlements nolon/nolon.entitlements`。
  - 新增 CloudKit bootstrap entitlement 判定测试。
- 验证：
  - `xcodebuild -project nolon.xcodeproj -scheme nolon-tests -configuration Debug -sdk macosx test CODE_SIGNING_ALLOWED=NO -only-testing:nolonTests/CodexiCloudSyncPresentationTests -quiet` 通过
  - `bash -n scripts/build-dmg.sh` 通过
- 风险与后续：
  - 需要基于修复后的签名脚本重新产出一个替代 `2.1.20` 的新版本。
  - Apple Developer 后台的 iCloud / CloudKit / Push 权限配置仍需继续完成，避免真机真容器联调阶段再次被外部能力阻塞。

## CloudKit 发布签名二次排障

- 背景：修复启动期 `CKContainer` 崩溃后，继续做本地真实安装验证，发现 app 仍可能在 launchd 阶段直接失败。
- 新证据：
  - 手工重签并带 `nolon/nolon.entitlements` 的 app，`codesign --verify --deep --strict` 与 `spctl -a -vv` 都通过。
  - 但从 `/Applications/nolon.app` 启动时，系统日志报：
    - `Unsatisfied entitlements: com.apple.developer.icloud-container-identifiers, com.apple.developer.aps-environment, com.apple.developer.icloud-services`
    - `No matching profile found`
    - `Launchd job spawn failed`
  - 同机用 Xcode 自动签名出的 Release 产物则正常包含 `Contents/embedded.provisionprofile`，并可成功拉起进程。
- 结论：
  - 对 macOS 上带 CloudKit / Push restricted entitlements 的 app，只补手工 `codesign --entitlements` 不够，必须同时嵌入匹配的 provisioning profile。
  - 否则会出现“签名校验看起来是绿的，但 AMFI 在进程启动前直接拒绝执行”的假绿状态。
- 已完成治理：
  - `scripts/build-dmg.sh` 新增 restricted entitlement 检测。
  - 若检测到上述 entitlement 且未提供 `EMBEDDED_PROVISION_PROFILE_PATH`，脚本会直接失败，不再继续产出 DMG。
  - 若提供 `EMBEDDED_PROVISION_PROFILE_PATH`，脚本会把 profile 写入 `Contents/embedded.provisionprofile` 后再完成 app 签名。
- 验证：
  - `bash -n scripts/build-dmg.sh` 通过
  - Xcode 自动签名 Release build：`xcodebuild -project nolon.xcodeproj -scheme nolon-app -configuration Release -destination 'platform=macOS' build -quiet` 通过
  - Xcode 产物含 `Contents/embedded.provisionprofile`，且进程可被 LaunchServices 拉起
- 后续：
  - 正式发布前，需要准备与 `nolon.overloaded.com`、CloudKit、Push capability 匹配的 provisioning profile，并以 `EMBEDDED_PROVISION_PROFILE_PATH` 输入发布脚本，或改走 Xcode 官方签名产物链路。

## 发布链路切换到 Xcode 官方签名产物

- 背景：用户要求不再继续沿用“`CODE_SIGNING_ALLOWED=NO` + 手工 `codesign`”链路，直接改走 Xcode 官方签名产物。
- 验证结论：
  - `xcodebuild archive` 可以成功产出 archive。
  - `xcodebuild -exportArchive` 在 `method=developer-id` 下若缺匹配 profile，会明确失败：`No profiles for 'nolon.overloaded.com' were found`。
  - 这比手工重签更可靠，因为 Xcode 会在导出阶段就拦住“证书/entitlement/profile 不匹配”的假绿状态。
- 已完成改造：
  - `scripts/build-dmg.sh` 默认改为：
    - `USE_XCODE_OFFICIAL_SIGNING=1`
    - `xcodebuild archive`
    - `xcodebuild -exportArchive`
  - 新增环境变量：
    - `XCODE_EXPORT_METHOD`，默认 `developer-id`
    - `XCODE_SIGNING_STYLE`，默认 `automatic`
    - `XCODE_SIGNING_CERTIFICATE`
    - `XCODE_PROVISIONING_PROFILE_SPECIFIER`
  - `.github/workflows/release.yml` 新增：
    - `MACOS_PROVISIONING_PROFILE_BASE64`
    - `XCODE_PROVISIONING_PROFILE_SPECIFIER`
    - workflow 会先安装 provisioning profile，再执行 release
  - `scripts/build-dmg.sh` 在 `developer-id` 导出模式下，若缺 `XCODE_PROVISIONING_PROFILE_SPECIFIER` 会在构建前直接失败，不再等到 archive/export 半途报错
  - release runbook 已同步改成“官方签名链路 + profile secrets”说明
- 验证：
  - `bash -n scripts/build-dmg.sh` 通过
  - `bash -n scripts/release.sh` 通过
  - `.github/workflows/release.yml` YAML 解析通过
- 当前边界：
  - 仓库链路已切换到 Xcode 官方签名产物。
  - 真实发布仍依赖一份可用于 `developer-id` 导出的 macOS provisioning profile 输入到 CI secrets。
