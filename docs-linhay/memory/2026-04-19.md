## Codex Sessions 排序链路优化
- 结论：当前“首屏列表出现很快，但排序规则慢”的主因不在磁盘扫描，而在 `CodexSessionsTabViewModel` 的内存侧排序重建链路。
- 决策：bucket 只保留 membership，不在 `upsert/insert` 阶段做整桶排序；section rows 的排序职责统一收敛到 `makeSectionState(...)`。
- 实现：`apply(snapshotPresentation:)` 改为批量重建 `rowsByID/project buckets/provider buckets`，避免首屏 hydrate 时每条会话都触发 project/provider 双重重排。
- 实现：搜索路径也改为只在 section state 构建时排序一次，去掉多处重复 `sessions.sorted(...)`。
- 新增测试：`recent` 模式下 usage 回填完成后，section 和 row 顺序保持 recent，不会因为后台 usage 加载而改序。

## Codex Sessions 首屏 Usage 排序
- 根因确认：`sortMode` 能从偏好恢复为 `usage`，但首屏命中 `cached snapshot` 时，`usageBySessionID` 还没有预热，`usageOrderingValue(for:)` 对所有项都返回占位值，排序因此回退到时间。
- 决策：不改现有 `sortSessionRows` / `sortSections` 语义，只在首屏 `cached snapshot` 与其他 initial full snapshot 应用前，同步读取 usage index，补齐首屏排序键。
- Provider 侧新增 `loadCachedSessionUsage(codexHome:rolloutPath:)`，返回 `CodexSessionCachedUsageLookupResult`，仅命中 SQLite usage index，不触发 rollout 文件重扫。
- `CodexSessionsTabViewModel` 新增 `CodexSessionsTabUsageIndexServicing` 协议；当 `sortMode == .usage` 且是 initial snapshot 应用时，先把命中的 totals 写入 `usageBySessionID`，再走现有 section rebuild。
- 新增 BDD 回归：`GivenPersistedUsageSortAndFreshCachedSnapshot_WhenLoading_ThenInitialSectionsAndRowsAlreadyFollowUsageOrder`，锁定“首屏首次展示就按 usage 排”的语义。

## Codex Sessions SQLite 容错
- 根因：`CodexSessionStore.loadStateIndex(in:)` 会把单个 `state_*.sqlite` 的打开失败直接抛出，导致整个会话页加载失败，和既定“warning + skip”降级策略不一致。
- 修复：对每个 `state_*.sqlite` 单独捕获 SQLite 读取错误；失败时发 `CodexSessionStore.warningNotification`，附带 `database_path`，并跳过该坏库继续合并其余状态库。
- 新增回归：存在一个不可读 `state_bad.sqlite` 且同时存在正常 `state_4.sqlite` 时，`loadSnapshot` 仍成功，且会记录 warning。
- 验证：`swift test --package-path libs/Providers --filter CodexSessionStoreTests` 通过，日志中已确认 warning 文案包含 `skipped unreadable state database ... unable to open database file`。
