## Codex 用量根因确认（21:xx +0800）
- 已根据新增证据把 “根因候选” 收敛为“已确认的两条根因链”：
  - App 内手动刷新链路：
    - `ProviderUsageEngine+CodexRefresh.shouldRetainExistingCodexSuccessResult(...)` 只要已有 `.success` 就恒为 `true`。
    - 失败时不会替换旧 success，也不会清 `usage_cache`。
    - `reloadCodexFromDisk(...)` 又会把 persisted `usage_cache` 重新恢复成 `.success`。
  - 外部 CLI/其他进程写回链路：
    - 外部刷新主要更新 SQLite metadata 字段。
    - App 的 `CodexSQLiteObservationSnapshot` 只比较四张表的 `COUNT(*)`，metadata-only update 会被本地去重吞掉，导致不触发 reload。
- 新的统一表述：
  - 当前 Codex 用量系统对 success snapshot 有完整写入路径，但对 freshness invalidation 和跨进程 metadata 变更感知都不完整。

## Codex 用量新证据复核（21:xx +0800）
- 已复核新进场的 `auth polling / auth hash` 证据。
- 结论：
  - 这条证据不会推翻“外部 CLI metadata-only 写回不会触发 App reload”。
  - `startProviderAuthPolling(for:)` 只覆盖 provider `auth.json` 哈希变化，再把凭证 payload 回灌 SQLite。
  - App 侧 `currentCodexAuthHashHex` 也只用于辅助识别 active account，不用于 usage reload 判定。
  - 因此它只能说明“仓库里存在凭证文件变化的同步链路”，不能说明“usage metadata 变化会被 UI 感知”。
- 当前根因判断保持不变：
  - 根因 1：App 内刷新失败后继续保留旧 success / usage cache。
  - 根因 2：外部 CLI 写回 SQLite metadata 时，App 的 count-only observation 会吞掉变更。
