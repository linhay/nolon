- 用户反馈：`Codex Sessions` / `Intraday Drilldown` 相关链路在全量文件场景下可能占用到约 `11G` 内存，并明确要求“流式读取计算，而不是一次性吃进内存”。
- 现场诊断：
  - 运行中 `nolon` 进程在排查时 `physical footprint` 已回落到约 `580MB`，但存在大量 swap，说明更像是某条读取链路触发过瞬时峰值。

    - `CodexSessionsTabViewModel.refreshProjectedOverviewUsage()` 只是为了显示总量文案；
    - 旧实现却调用 `CodexSessionStore.loadProjectedUsageMinutes()`，进一步在 `CodexSessionUsageIndex.loadProjectedUsage()` 中先物化全量 minute entries 数组，再做逻辑 session 去重合并。
- 本次落地：
  - `CodexSessionUsageIndex` 新增 projected summary 聚合能力，改为数据库侧按 `logical_session_id + minute` 去重，再按 `minute` 汇总，Swift 侧逐行累计 `totalTokens`，不再为顶部总量物化完整 minute entries。
  - `CodexSessionStore` 新增 `loadProjectedUsageSummary(...)` / `loadCachedProjectedUsageSummary(...)`，沿用现有索引预热与 stale purge 流程，但返回 summary 而不是全量 minute 数组。
  - `CodexSessionsTabViewModel` 顶部 overview usage 改为优先消费 projected summary；UI 为总量文案不再触发完整 projected minute 明细加载。
  - 同时保留 minute 真源能力，`Intraday Drilldown` 仍可在真正需要明细时读取 minute 级数据。
  - 继续修正 `Intraday Drilldown` 慢加载：`CodexQuarterHourUsageFetcher` 默认改为先读 `loadCachedProjectedUsageMinutes(...)`，只有显式 `forceRefresh` 或 cached 结果为空时才回退 `loadProjectedUsageMinutes(...)` 做 live 预热，避免普通 drilldown 每次都重扫全量 rollout。

## Codex 用量单日差异 2-3 倍排查结论
- 现象：用户反馈 `nolon` 的 `Codex -> 用量` 单日统计显著高于 `ai-proxy-api`，量级稳定在 `2-3` 倍；用户确认实际流量都经过 proxy，因此需要排查“本地 session 统计”与“proxy usage_records 日趋势”是否存在结构性口径差异。
- 已坐实的代码事实：
  - `nolon` 当前 Codex token trend 仍明确走 `fetchRefreshedGlobalSnapshot(...)` / `fetchGlobalSnapshot(...)`，调用前主动移除 `CODEX_HOME`，因此读的是全局 `~/.codex`，不是当前账号隔离目录。
  - `CodexSessionScanner.scanFiles(...)` 默认 `includeArchived = true`，`CodexSessionStore.scannedFiles(...)` 与 vendored `CostUsageScanner` 也都显式带 `includeArchived: true` / `includeArchivedSibling: true`，所以 live 与 archived rollout 都会进入当前用量统计。
  - `CodexSessionEventParser.reduceUsageLine(...)` 会把所有 `token_count` 增量直接累计到 projected usage，不区分该次请求最终是否成功。
  - `CodexSessionUsageIndex.enumerateProjectedMinuteTotals(...)` 只按 `session_id`（为空时退回 `rollout_path`）做 logical session 去重；`forked_from_id`、`originator`、`source` 都不会参与归并，因此不同 `id` 的 subagent / explorer / forked rollout 会被当成独立会话累计。
  - `ai-proxy-api` 的 monitor daily trend 明确只从 `usage_records` 聚合 `failed = 0` 的 token；失败请求只计数，不计 token。
  - `ai-proxy-api` 的 Codex 流式 executor / websocket executor 只有在收到 `response.completed`（或 websocket 的 `response.done`）且能解析出 `response.usage` 时才会 `Publish` usage record；与其他 executor 不同，这两条流式链路没有在成功结束时补 `EnsurePublished()`，因此“成功但最终 completion 没带 usage”的请求会直接缺失于 daily trend。
- 抽样验证（`~/.codex/sessions/2026/04/21`）：
  - 当天共有 `12` 个 rollout；只有 `2` 个是顶层 `vscode` 会话，另外有 `7` 个 rollout 明确属于 subagent / explorer 派生线程。
  - 采用与 `CodexSessionEventParser` 一致的 token delta 规则重放后，当天本地总量约 `1,103,365,738` tokens，其中：
    - 顶层 `vscode` 会话约 `340,726,567`
    - `subagent` 会话约 `760,115,655`
  - 也就是说，仅 subagent 这一项就占了当天本地总量的约 `68.9%`，把总量抬到了顶层会话的约 `3.24x`，足以单独解释用户看到的 `2-3` 倍差距。
- 当前判断：
  - 这次差异不是 cached token 被重复加总；`nolon` 当前趋势页 `totalTokens` 仍按 `input + output` 统计，cached 只是单列展示。
  - 当前 `2-3` 倍差异的主因更偏向 `nolon` 本地页偏大：全局 `~/.codex` + live/archived + 不折叠不同 `id` 的 subagent/explorer + 不区分请求成败。
  - `ai-proxy-api` 侧也存在低估风险：daily trend 只算成功请求，且 Codex 流式链路存在“成功但未 publish usage record”的漏记窗口，所以它同样不能视为绝对真实值。
- 后续动作建议：
  - 先把 Codex 用量页的 scope 收回到当前账号 `CODEX_HOME`，不要默认读 global `~/.codex`。
  - 为 projected usage 增加“是否折叠 `forked_from_id` / subagent”产品决策与对应测试，再决定是否把派生线程并回父线程统计。
  - 补 `ai-proxy-api` 的 Codex 流式成功兜底：若成功结束但未解析到 usage，也至少 `EnsurePublished()` 一条 0-token 成功记录，避免 daily trend 漏请求。
  - 若要让两端真正可对齐，需要先统一产品定义：到底比较“所有本地 session token 消耗”，还是“proxy 成功请求 token 聚合”。

## Codex forked/subagent 用量口径修复
- 用户进一步明确产品语义：`nolon` 默认按全局 `~/.codex` 统计本身没有问题，但 `subagent` / `forked` rollout 只应该统计 fork 之后新增的用量，不能把父线程继承过来的 cumulative usage 一并算进 child。
- 根因确认：
  - `CodexSessionUsageIndex.parseUsageFile(...)` 之前会把派生 rollout 第一条 cumulative `total_token_usage` 直接当作新增 delta 写入 `session_usage_minutes`。
  - 对带 `forked_from_id` 的 rollout，这条首包实际上经常是 inherited baseline，所以会把父线程已有上下文重复算到 child，放大全局 summary / trend / session usage。
  - 同时旧实现允许这类 rollout 在文件 append 后继续走 `deltaAppend`，而当前 schema 又没有单独持久化 raw baseline，后续刷新也存在再次污染 totals 的风险。
- 本次实现：
  - `CodexSessionUsageIndex.load(...)` 通过首个 `session_meta.forked_from_id` 判定 derived rollout。
  - 对 derived rollout，第一条可识别 cumulative total 只建立 baseline，不进入 minute facts；`usage_entries.totals` 对外暴露的 totals 也改为 `raw totals - baseline`。
  - derived rollout 一旦文件变化，强制退回 `fullRebuild`，不再走 `deltaAppend`。
  - 新增 Provider 测试覆盖：
    - projected summary 只统计 fork 后 delta；
    - derived rollout append 后仍保持 `fullRebuild` 与正确 totals。
- 验证：
  - `swift test --package-path libs/Providers --filter CodexSessionStoreTests` 通过，含新加的 forked 用例。

## Codex Usage 刷新详情与进度反馈
- 用户现场反馈：`Codex -> Usage` tab 刷新时长期只看到 spinner，感知上像“页面卡住”，希望刷新期间能看到明确的阶段说明与进度。
- 本次收敛：
  - `CodexSessionStore.refreshChangedProjectedUsageDayKeys(...)` 追加分阶段性能通知，显式区分 `started / progress / completed`，并补充扫描文件数、缓存命中数、dirty rollout 数、processed rollout 数、受影响天数等 payload。
  - `ProviderUsageEngine` 仅在 `codex` 用量页监听当前 `codex_home_path` 的通知，把底层 payload 翻译成页面文案，形成 `正在准备刷新本地用量 -> 正在扫描会话用量 -> 正在回填派生用量` 的连续状态。
  - `ProviderTokenTrendSection` header 下方新增刷新状态卡片，展示标题、详情、`processed / total` 进度文案与 progress bar，避免用户误判为纯卡死。
- 追加细化：
  - 刷新 phase 进一步细化到文件级 / 数据库级，页面现在可以区分 `扫描清单 -> 读取 usage-index -> 读取旧 minute -> 分析 rollout -> 回读 minute -> 清理旧索引`。
  - 详情会带上当前 rollout 相对路径、数据库名，以及刷新原因（如 `发现新 rollout` / `live rollout 指纹变化`），方便直接判断卡在哪一步。
  - 根据现场反馈，刷新状态卡片又进一步收口为“标题 + 分析说明合成一条主文案”，不再拆成上下两行，降低阅读跳跃感。
- 产品边界：
  - 这次只增强“刷新可解释性”，不改 token trend 汇总口径。
  - 当前进度百分比基于 dirty rollout 数，不是字节级精确进度；若后续仍出现真实卡住，可直接据此判断堵在扫描还是回填阶段。

  - `xcodebuild test -project nolon.xcodeproj -scheme nolon-tests -destination 'platform=macOS' -only-testing:nolonTests/ProviderUsageEngineManualRefreshTests -only-testing:nolonTests/ProviderUsageRootLoadBoundaryTests` 通过。
