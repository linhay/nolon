## 2. 负反馈记录
1. **Enable/Disable 按钮位置**：用户希望按钮放在 Workflow 按钮右侧常驻显示，并且样式与 Workflow 一致（而不是只放在右上角菜单或单独 badge）。
2. **Enable/Disable 颜色区分**：用户指出 enable/disable 不应同色；期望两者有不同颜色（例如 enable 提示性更强）。
3. **切换状态不应改变排序**：用户指出点击 disable/enable 后列表发生重排不符合预期；希望切换仅改变状态，不改变当前列表顺序。
4. **workflows 扫描误判**：用户指出某些 Markdown（例如 README/文档页）没有 workflow 头部格式却被识别为 workflow；要求 workflow 必须带 YAML frontmatter（`--- name/description ---`）。
5. **命名语义**：`SkillParser.swift` 实际承担了通用 frontmatter 解析，用户质疑文件名不准确，建议拆分通用解析器并让 `SkillParser` 聚焦于 `SKILL.md -> Skill`。

## 3.5 习惯/风格学习（偏好沉淀）
- **文件系统操作偏好（仓库级）**：当项目已依赖 `STFilePath` 时，新增/修改文件 IO、目录枚举、拷贝/移动/删除、symlink 等操作优先使用 `STFilePath`，避免混用 `FileManager`。
- **UI 偏好（Card/列表交互）**：
  - 状态切换（enable/disable）应作为常驻按钮放在 Footer 的主要操作区（例如放在 Workflow 右侧），并复用同一套按钮风格。
  - 切换 enable/disable 不应触发重排；默认按稳定规则排序（如按名称）或保持原顺序。
- **Workflow 识别规则（仓库级）**：
  - 仅当 Markdown 文件包含 YAML frontmatter 且包含 `name` 与 `description` 时，才将其视为 workflow。
  - 不应把 README/文档页当作 workflow（即使内容含有 “workflow” 字样）。
- **命名与职责分离（仓库级）**：
  - 通用 frontmatter 解析抽取为独立组件（例如 `FrontmatterParser`）。
  - `SkillParser` 仅负责 SKILL.md 的语义解析（`Skill` 模型），避免“名不副实”导致误用。
